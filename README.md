# CrossApp
 Наскрізний проєкт з крос-платформного програмування.
 Предметна область: Замовлення. Сутності: Customer, Product, Order, OrderLine.
 Призначення: оформлення замовлень і підрахунок сум.

## Build

Для збірки проєкту використовується команда:

dotnet build

## Run

Для запуску консольного застосунку:

dotnet run --project src/Cli -f net10.0

Поточний етап проєкту — лабораторна 7: LINQ-звіти для замовлень. Без аргументів програма показує топ-5 клієнтів за сумою замовлень.

## Publish
### Self-contained

Публікація застосунку разом із необхідним .NET Runtime:

dotnet publish src/Cli -c Release -r osx-arm64 --self-contained true -p:PublishDir=bin/publish-self-contained/

### Framework-dependent

Публікація застосунку без .NET Runtime:

dotnet publish src/Cli -c Release -r osx-arm64 --self-contained false -p:PublishDir=bin/publish-framework/

### Single-file

Публікація self-contained застосунку в одному виконуваному файлі:

dotnet publish src/Cli -c Release -r osx-arm64 --self-contained true -p:PublishSingleFile=true -p:PublishDir=bin/publish-single-file/

У результаті каталог publish містить один основний виконуваний файл. Після публікації необхідно перевірити кількість файлів, розмір каталогу та можливість запуску застосунку.

### Trimmed

Публікація self-contained застосунку з trimming:

dotnet publish src/Cli -c Release -r osx-arm64 --self-contained true -p:PublishTrimmed=true -p:PublishDir=bin/publish-trimmed/

Trimming видаляє код, який аналізатор вважає невикористовуваним, що дозволяє зменшити розмір застосунку.

## Результати publish

| RID | Режим | Розмір publish | Потрібен runtime |
|---|---|---:|---|
| osx-arm64 | self-contained | 83 MB | ні |
| osx-arm64 | framework-dependent | 172 KB | так (.NET 10) |
| osx-arm64 | single-file | 76 MB | ні |
| osx-arm64 | trimmed | 20 MB | ні |


Self-contained версія має більший розмір, оскільки містить необхідний .NET Runtime і тому не потребує його попереднього встановлення.

Framework-dependent версія має значно менший розмір, але для її запуску необхідний встановлений .NET Runtime відповідної версії.

Single-file дозволяє об'єднати застосунок в один виконуваний файл, що спрощує його поширення.

Trimming дозволяє зменшити розмір застосунку шляхом видалення невикористовуваного коду.

## Multi-targeting

Бібліотека Core підтримує цільові платформи net8.0 та net10.0.

У Core.csproj використовується:

<TargetFrameworks>net8.0;net10.0</TargetFrameworks>

Для визначення версії збірки використовується умовна компіляція:

if NET10_0_OR_GREATER
const string BuildNote = "збірка під net10.0";
else
const string BuildNote = "збірка під net8.0";
endif


## Інваріанти предметної області 
- **ID замовлення та клієнта** не можуть бути порожніми при створенні замовлення.
- **ID та Назва товару** не можуть бути порожніми при додаванні рядка.
- **Ціна товару** не може бути від'ємною (`>= 0`).
- **Кількість товару** у рядку має бути більшою за нуль (`> 0`).
- **Додавання рядків** можливе лише до замовлення у статусі `Draft` (Чернетка). Не можна змінювати підтверджене або скасоване замовлення.
- **Підтвердження замовлення** (`Confirm`) неможливе, якщо в ньому немає жодного рядка (порожнє замовлення).
- **Зміна статусів** (Підтвердження або Скасування) неможлива, якщо замовлення вже підтверджено або скасовано.
- **Інваріант, що охоплює ДВІ сутності:** 
Реалізовано правило: "Один клієнт не може мати більше 3-х відкритих (Draft) замовлень".
Це правило знаходиться у класі `OrderService`, а не в самій сутності `Order`.



## Сервісний шар та сховища (Лабораторна 5)

- **Інтерфейс сховища:** `IOrderStore` (`Core.Abstractions`)
- **Реалізації сховища:**
  - `InMemoryOrderStore` (`Core.Storage`) — робота в оперативній пам'яті на основі `Dictionary`, підтримує початкове заповнення (`seed`).
  - `FileOrderStore` (`Core.Storage`) — файлове збереження у форматі JSON із кешуванням у пам'яті та записом змін на диск (`Flush`).
- **Сервіс:** `OrderService` (`Core.Services`) — інкапсулює бізнес-операції над замовленнями (`CreateOrder`, `AddLine`, `Confirm`, `All`, `Find`), залежить виключно від абстракції `IOrderStore`.
- **Впровадження залежностей (DI):** ручне впровадження через первинний конструктор у точці входу (`Program.cs`) з перемиканням реалізації за допомогою аргументу `--file`.

### Додаткові завдання (Лабораторна 5)

1. **Декоратор `CachingOrderStore` (`Core.Storage`):**
   - Реалізує патерн Decorator для контракту `IOrderStore`. Приймає інший екземпляр `IOrderStore` через первинний конструктор і кешує запити в пам'яті, зменшуючи навантаження на базове сховище.

2. **Пошук з параметром `Func<Order, bool>`:**
   - У контракт `IOrderStore` та сервіс `OrderService` додано метод `Find(Func<Order, bool> predicate)`, що дозволяє гнучко фільтрувати замовлення за довільними предикатами (наприклад, за статусом або сумою).

3. **Фабрика `StoreFactory.Create(args)` та порівняння з «усе в Program.cs»:**
   - Створено клас `StoreFactory`, що інкапсулює аналіз аргументів командного рядка (`--file`, `--cache`) та створення відповідного ланцюжка сховищ.
   - **Порівняння:**
     - *«Усе в Program.cs» (Composition Root):* простий і прозорий підхід для невеликих додатків, де точка входу сама вирішує, які екземпляри створити. Проте за потреби повторного використання логіки вибору сховища (наприклад, у тестах або додаткових CLI-інструментах) виникає дублювання коду.
     - *`StoreFactory`:* виносить логіку вибору та конфігурації сховищ (включно з огортанням у декоратори) в окремий компонент, усуває дублювання та спрощує розширення новими типами сховищ, але створює залежність фабрики від формату аргументів запуску.

## Доменні події та делегати (Лабораторна 6)

- **Тип події:** `OrderChangeKind` (`Core.Events`) — перелічення змін: `OrderCreated`, `LineAdded`, `OrderConfirmed`, `OrderCancelled`.
- **Дані події:** `OrderChangedEventArgs` (`Core.Events`) — містить `OrderId`, `Kind`, `LinesCount`, `Total` та часову мітку `At` (`DateTimeOffset.Now`).
- **Публікація події:** у сервісі `OrderService` оголошено `event EventHandler<OrderChangedEventArgs>? Changed`. Подія безпечно піднімається через `Changed?.Invoke(...)` виключно після успішної зміни стану та збереження в сховищі.
- **Підписники в Cli (`Program.cs`):**
  1. Локальний метод `OnOrderChanged`: виводить інформацію про зміну замовлення в консоль та записує її у файл `logs/app.log`.
  2. Лямбда із замиканням `(_, _) => changes++`: рахує загальну кількість отриманих подій.
- **Демонстрація відписки (`-=`):** після виклику `service.Changed -= OnOrderChanged` подальші операції не виводяться в консоль і не записуються у лог, проте лічильник у лямбді продовжує фіксувати зміни.
- **Відмова інваріанту:** при помилці операція переривається винятком, тому подія не публікується.
- **Делегат замість події:** метод `FindAll(Func<Order, bool> predicate)` використовує функціональний делегат `Func` для фільтрації даних за довільним критерієм.

### Додаткові завдання (Лабораторна 6)

1. **Інтерфейс `INotificationSink` та реалізації `ConsoleSink`, `FileSink`:**
   - Оголошено інтерфейс `INotificationSink` (`Core.Abstractions`) із методом `Notify(OrderChangedEventArgs args)`.
   - У проєкті `Cli` створено дві реалізації: `ConsoleSink` (вивід у консоль) та `FileSink` (дописування у файл).
   - `OrderService` підтримує ручне впровадження залежності `INotificationSink?` через конструктор.
   - **Порівняння підходу з інтерфейсом та підходу з подією (`event`):**
     - *`INotificationSink` (Dependency Injection):* фіксований контракт, сервіс безпосередньо залежить від абстракції приймача сповіщень. Зазвичай передається лише один екземпляр під час ініціалізації сервісу (або потрібен додатковий патерн `CompositeSink`). Зв'язування відбувається в момент створення об'єкта.
     - *`event EventHandler<...>` (Observer):* слабке зв'язування (decoupling) — сервіс нічого не знає про споживачів сповіщень. Підписників може бути скільки завгодно, вони можуть динамічно реєструватися (`+=`) та відписуватися (`-=`) під час виконання програми без зміни чи перезапуску сервісу.

2. **Делегат `Action<string>` у методі імпорту:**
   - У метод `ProductCsvImporter.Load(string path, Action<string>? onSkippedLine = null)` додано функціональний делегат `Action<string>`. При виявленні пошкоджених рядків викликається колбек `onSkippedLine`, що дозволяє викликачу наживо реагувати на дефектні дані під час читання файлу.

3. **Чому async-обробник події — це `async void`, і чим це небезпечно:**
   - *Чому `async void`:* Сигнатура стандартного делегата подій у .NET — `void EventHandler(object? sender, EventArgs e)` або `void Action(...)`. Тип повернення делегата жорстко зафіксований як `void`. Відповідно, асинхронний метод чи лямбда, підписані на таку подію, змушені мати сигнатуру `async void`, оскільки сигнатура `async Task` не сумісна з типом повернення `void` делегата події.
   - *Чим це небезпечно:*
     1. **Неможливість відловити винятки (Unhandled Exceptions):** У методах із `async Task` будь-який виняток загортається в об'єкт `Task`, і його можна перехопити через `try/catch` під час `await`. У методах `async void` виняток не фіксується в жодному завданні — він викидається безпосередньо в поточний контекст синхронізації або пулу потоків, що за замовчуванням призводить до аварійного падіння всього процесу програми (Crash).
     2. **Відсутність очікування (Fire-and-Forget):** Викликач події (`Changed?.Invoke(...)`) не може використати `await` для очікування завершення роботи асинхронного обробника. Сервіс продовжує виконання далі, що призводить до стану гонитви (race condition), проблем із тестуванням та помилок під час звільнення ресурсів (disposal).

## LINQ-звіти (Лабораторна 7)

- **Сервіс звітів:** `ReportService` (`Core.Reports`) — приймає `IEnumerable<Order>`, формує звіти через LINQ to Objects і повертає DTO.
- **Звіти:** `TopCustomers` — топ-5 клієнтів за сумою; `ExpensiveOrders` — замовлення дорожче 200 грн; `ByStatus` — кількість і сума за статусом; `Totals` — загальна сума, середній та максимальний чек.
- **DTO:** незмінні `record` типи `CustomerSummary`, `OrderReportLine`, `GroupSummary`.
- **Сортування:** при однаковій сумі топ додатково сортується за ID клієнта через `ThenBy`. Для порожнього джерела звіти повертають порожні списки, агрегати — нулі.
- **Демонстраційні дані:** 18 замовлень у статусах `Draft`, `Confirmed`, `Cancelled`.

### Відкладене виконання

`Where` створює запит, який виконується під час перебирання, зокрема при виклику `Count()`.
У демо перший `Count()` повертає 10, а після додавання замовлення на 201 грн повторний виклик повертає 11.
`ToList()` фіксує результат: після очищення локального джерела знімок зберігає 11 елементів, а запит повертає 0.
